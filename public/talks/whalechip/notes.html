03
1 / 4 NVIDIA · ECO 自動化架構

一個 top agent 指揮，每個 partition 一個 agent 修

在 NVIDIA 我負責 GPU chip 的 timing ECO closure。每個 spin 都有大量 violation，分類、修、驗證、放行原本全靠人工，所以我做了一套自動化系統。先看全貌，接下來三頁再拆開講。

最上層是一個 top agent，用 LangChain 寫，透過我重寫的 LSF 派送開 session、對各 partition 下指令。

每個 partition 底下有一個 in-house agent，用 Claude Agent SDK 寫，照一套 skills 在 live session 裡修；它跟 top agent 透過我寫的 WebSocket hub 溝通，跨 partition 的問題也走 hub。最後一定是人審核才放行。

結果是一輪自動修正處理掉約 23 萬筆裡的 97%，setup TNS 從 −250 ns 收到大約 0；這套流程也跟同事一起在 NTECH China 2026 發表。

這套做法可以帶到團隊：重複、固定的 flow 寫成 skill 和自動化流程，人只看判斷和放行。

（動畫：P 暫停、逗號／句號一步一步走）

接下來一塊一塊講，先從 hub 開始。

04
2 / 4 NVIDIA · WebSocket Hub × Cross-Partition ECO

一個 WebSocket hub，讓 ECO 可以跨 partition

這是我寫的 WebSocket hub，in-house agent 跟 top agent 就是在這裡溝通。它可以接 PrimeTime、VC 這些工具的 session，再串我們 in-house 的 ECO 工具，每個 partition 一個 room。

有了它就能做跨 partition 的 ECO。舉例：A 的邊界有 skew，需要 B 那邊吸收幾個 ps。以前要找對方 owner、等回覆；現在 A 的 agent 把任務送進 B 的 room，B 的 agent 做一次核准過的本地試修，改完兩邊重新讀回，兩側都收斂才 keep。

右邊這個共享案件的畫面，是最後要介紹的平台；最後還是人審核才放行。這裡的元件都已經做好，整合流程還在 pilot 驗證。

可以帶到團隊的是：PT、VC 這類要培訓才會用的工具，包成 Claude Code 能直接連的介面，新人不用先把工具學熟就能開始查問題。

有了 hub，再來看每個 partition 的 in-house agent 怎麼修。

05
3 / 4 NVIDIA · In-house Agent × Skills

In-house agent 照 skills 修，人來放行

每個 partition 的 in-house agent 用 Claude Agent SDK 寫，照左邊這排 skills 一步步修：前檢、自動修、分類，再依 violation 類型分成 setup、hold、tran/cap、SI 各自的修法，讀回、出口檢查之後才放行。

分工是：agent 只做判斷，真正的改動透過 skill 叫 in-house ECO 工具，經剛剛那個 WebSocket hub 送到 LSF 上的 live session 執行；session 只往外連、不開 inbound。

三個原則：每次工具呼叫都是一個 skill、可以單獨重跑；讀回通過才算數，沒證據就是 pending；修不了的標 needs human。

底下是一筆 hold violation 實際走過的路：分類、擬最小改動並先算 setup 代價、派到 session、讀回、最後人來核准。

（動畫：逗號／句號一步一步走，最後點 HUMAN APPROVAL 放行）

session 一多，top agent 下指令用的派送本身就成了瓶頸。

06
4 / 4 NVIDIA · LSF Farm 派送 × ECO 平台

讓派送工具，不只是派送工具

最後一個，我想講的是讓派送工具不只是派送工具，分兩個重點。

第一，派送本身：top agent 就是透過它下指令。我重寫了公司派送 LSF 的 farm 機制。原本 job 送上 farm 就是黑盒子，只能一直輪詢；改寫後 session 主動回報。原型壓測對照原本的系統：吞吐量 3.2 倍、輪詢快 150 倍，而且 32 路並行下零重複派送——同一筆 ECO 改兩次就壞了，所以這點我最在意。

第二，不只是派送：因為每個 session 都會回報，派送工具就變成一個 ECO 平台。每一筆修正的狀態、歷史、agent 的提案都即時看得見，需要人的排最前面，剛剛跨 partition 的共享案件也是在這裡看，網頁讀取也快了 12 倍。

NVIDIA 的部分到這裡，接下來講前端。

07
1 / 3 Front-end · TSMC 數位設計實習

N7 ADPLL 數位區塊：運算單元共用

前端先講 TSMC 實習。2024 暑假參加 DTP，負責優化 N7 ADPLL 的數位電路。

做法是運算單元共用：原本三組運算各有一顆乘法器，算完才用 MUX 選其中一個結果，但同一時間只會用到一組。所以我把 MUX 移到乘法器前面，先選運算元、再乘，三組共用一顆乘法器；位寬不同的運算元先做 bit extension 對齊。

結果是 ADPLL 數位區塊功耗降 16%、面積降 21%，優化後續也被設計採用。

另外用 Verdi 把內部狀態機可視化來追行為，用 VC_STATIC 做 CDC、DFT 分析，也用 JasperGold 做形式驗證。

08
2 / 3 Front-end · MIMO Sphere Decoder · 8-PSK · K = 4

4×4 MIMO K-best sphere decoder

第二個是 4×4 MIMO 的 K-best sphere decoder，8-PSK、K = 4。上面是整體架構：先用 4 拍載入 QR 分解後的 R，之後 每拍進一筆 ŷ；四層各有 PDE 跟 SORT，每層兩級 pipeline、共 8 級，ŷ 每層延遲兩拍對齊。

左下是 PDE 的電路：每條候選算 ŷ 減掉 R 乘符號，取 |Re|+|Im| 當距離，再加上一層留下來的 PDE。乘符號的部分沒有用乘法器：8-PSK 的 ±1、±j 只是正負號或實虛部交換，對角點用 0.75 = 兩個移位相加代替 0.707（golden 的星座點也用 0.75）；8 個乘積每層只算一次，再用 path 的 3-bit symbol index 透過 8 選 1 MUX 分給各條候選。

右下是排序網路：32 筆分 4 組做 MERGE8，再兩兩 MERGE16 各留 4 筆，最後 8 取 4；比的是 12-bit 的 PDE，整筆 24-bit 紀錄一起交換。第 4 層取最小的那條，path 轉回符號輸出。

（被問到是不是完整排序時）最小值一定正確，所以最後的最佳路徑沒問題；第 1 層因為 8-PSK 的距離照角度排是 bitonic，8 取 4 也是準的（8 個數字所有繞圈單峰的排列 512 種全試過）。但第 2、3 層留下的 4 條不保證是真正的前 4 名，這套網路比完整排序少了幾級比較，等於近似、K 打了折；golden 用的是同一套網路，所以 bit-exact 一致。

（動畫：每層的 PDE 畫成疊起來的卡片，×8、×32 就是並排的硬體套數，每一套算一條候選的距離；PDE 那一步整疊一起亮，表示同一拍並行算完。SORT 那一步排序網路亮、出來 4 個橘點是留下的 4 條，右上框的 path 多長 3 bit。四層各自一套硬體、完全展開不共用：PDE 電路共 104 套、比較器共 280 個，所以每拍能吃一筆 ŷ。下面兩個面板跟著當下那一級亮。path 用的是 testbench 第 1 筆 ŷ 的真實結果。）

合成用 N16 標準元件：cycle time 0.71 ns、面積約 42,337 µm²；VCS 跟 MATLAB 定點 golden 比對，1,056 bits 全部一致。

3 / 3 Front-end · Quantized CNN · 手勢辨識 20 類

QAT INT8 CNN：從量化訓練到 APR

第三個是 QAT 量化的 INT8 CNN，做手勢辨識、20 類。

精度是分三步轉的：先在 FP32 模型插 fake-quant 做 QAT，用 fbgemm 的設定訓練 20 個 epoch；再用 convert() 轉成真正的 INT8 模型，權重 INT8、per-channel，activation UINT8；最後匯出給 RTL：bias 換算成 INT32，每通道的 scale 換成 Q31 乘數加 shift。

硬體上 MAC 累加是 INT32，每一層輸出都要 requant：acc 乘上每通道的 Q31 乘數再右移、加 zero point、clamp 到 0–255。這個乘法很寬，我把它拆成 7 級 pipeline：乘法拆兩段、再合併、64-bit 捨入加法分兩拍、移位，最後加 zp 並 clamp。

資料流一拍進一個像素：兩條 line buffer 依欄定址存前兩列，每列再接 3 級 shift 組出 3×3 視窗，新像素從右邊進來。conv1 是 4 個 PE、conv2 用時間多工跑 6 個通道，總共 84 個 MAC 乘法器，requant 另外 7 組。

實作：DC 合成在 TSMC 0.13、100 MHz，面積約 88 萬 µm²；Innovus APR 完 post-route setup WNS +1.30 ns、setup 沒有違規；hold 還有 2 條、差不到 0.001 ns，另有少量 max cap / tran / fanout 要收。

這部分可以延伸到團隊：波形也可以做成 Claude Code 看得懂的工具，幫忙 debug；這個我還沒做過，但做法跟接 PT、VC 一樣。

（被問到準確率）50×50 版 INT8 98.38%、10×10 完整版 97.75%；合成的是 10×10 縮小版（4/6/6 通道），那版的準確率沒有留紀錄；選 epoch 用的也是 test set，數字偏樂觀。

（被問到驗證）golden 從 PyTorch INT8 模型逐層抓，testbench 逐拍比 20 個輸出；最後一次留下紀錄的比對（4 月）還差 1–2 LSB，原因是 golden 跟匯出的參數來自不同 checkpoint、加上累加器先截 8 bit；之後 RTL 跟 golden 都改過，目前狀態要重跑確認。

Research · 台大碩士研究 · GrAPL @ IPDPS 2026

CHROMA：高品質圖著色搬上多 GPU

再來是碩士研究 CHROMA，多 GPU 的圖著色框架，發表在 IPDPS 2026 的 GrAPL workshop。

背景是：品質好的平行圖著色跑得慢，快的方法上色品質又差。品質好的 smallest-last 排序是循序的，priority allocation 在 CPU 上可以比上色本身慢 100 倍。

左邊是架構：每張 GPU 先做 priority allocation，我們的 cuSL 把它平行化，再加三個優化：ELS 提高掃描效率、EGC 用 θ 控制每輪的粒度、SDC 校正最小度數保住品質；上色沿用 ECL-GC 的 kernel。多 GPU 時用 RGP 切圖，邊界先上色、子圖帶 ghost vertex。

右邊是 JP 上色的過程：比自己優先的鄰居都上完色，就挑最小的可用顏色；同一輪可以很多點一起上色，所以適合 GPU。

結果在單張 RTX 4090 上，顏色數不變、幾何平均快 7 倍；比 192 執行緒的 CPU 版快 17 倍。

CHROMA 的程式基本上都是我寫的：GPU 上的 priority allocation、多 GPU 的 RGP 模組和 CPU baseline。這跟硬體設計的思路很像：找出循序的瓶頸、拆成能平行的結構、再處理同步。

（動畫：P 暫停、逗號／句號一次前進一輪）

（被問到履歷上的 14× 時）那是只開 ELS 的最快設定，顏色數會多三成多；顏色數不變的是 7.14 倍，所以簡報用這個數字。

Side Projects · 面試前兩週

兩個練習：Async FIFO 與 DRAM command scheduler

這一頁是我知道要面這個 team 之後，這兩週自己做的兩個練習，針對 JD 上的 CDC 和 memory controller。

Async FIFO：Cummings FIFO1 的結構，Gray 指標過兩級同步器。重點不在寫出來，而是驗證和約束：SVA 在 testbench 裡同時看兩邊的二進位指標，證明 full 和 empty 只會保守不會錯；DC 跑了兩套 SDC，一套 clock groups、一套 -allow_paths 加 max_delay 壓 Gray 匯流排，PT 最後故意把 clock groups 拿掉，看到 STA 拿兩個週期的公因數 0.1 ns 當要求。另外做了 jitter 注入：同步器第一級隨機晚一拍，Gray 版全過，二進位指標的對照版同步後會出現從未存在的值。

DRAM scheduler：controller 三層裡的中間那層。8 個 bank 各自的狀態機和計數器、rank 層的 tRRD、tFAW、tCCD、tWTR、tRFC，排程是 open-page 加 FR-FCFS，refresh 欠到 8 次才強制，輸出是 DFI 風格的命令腳位。驗證是 Python 寫的 PHY 加 DRAM 模型，隨機讀寫兩千九百筆全對；每條 JEDEC 時序各一條 assertion，把 tRCD 偷改短兩拍馬上被抓到。SMIC 0.13 合成 200 MHz 剛好過，關鍵路徑在排程器的優先順序鏈。

後來又補了：讀寫優先權加 write drain 加年齡上限、CKE 的 power-down 和 self-refresh、APB 可程式時序和效能計數器、DDR4 bank group 的 L/S 時序、(72,64) SECDED ECC、一個最小的 UVM 環境加 covergroup、DC 自動 clock gating 加 UPF 把排程核心做成 self-refresh 時可以斷電的電源域，GLS 和 Formality 確認 netlist。最後把另外兩層也做了：前端兩個 AXI port 拆 burst、ROB、HPR/LPR 仲裁加限流、RBC/BRC/XOR 位址對應；後端 DFI 1:2、PHY 的數位部分、上電初始化、MRS、ZQ、write leveling、read gate training、DFI sideband，測試台到 pin-level 的 DDR3 模型，三個時脈用 generated clock 合成。沒做的我也清楚：PHY 的類比部分、DFI 1:4、per-bank refresh、DFT。被問到可以講加在哪裡。

Side Project · 量化投資 · 自有資金實盤

量化投資系統

這套是用自己的錢在實盤跑的。

上面是實盤流程，每個交易日美東 10:05 由 systemd 自動跑：抓資料、算 12-1 動能取前 10 檔，中間有三道閘門：新聞否決、下單前檢查、最後對帳。任何一關不過就 fail-closed，不下單或直接中止；抓不到新聞也算不過。

離目標 ±20% 以內不動，這個帶寬在回測裡把手續費降了 81%。訂單是六狀態的狀態機，cid 用 hash 產生，重送也不會重複下單。

下面三個是共用模組：Rust 的部位計算核心，研究跟實盤共用同一份；斷路器 −35% 停買、−40% 出清；看門狗只讀不寫，有異常就發 Telegram。也做過一次 fail-closed 稽核，補上 3 個 critical、4 個 high 的漏洞。

研究端是我用 Rust 寫的因子引擎，一條公式從 10 秒變 63 毫秒；用 golden 案例驗證，故意注入 41 個 bug 抓到 38 個。

結果我照實說：右下這張是用現在的規則、含已下市股票的資料，回測 2010 到 2026 年。長期年化 18.6%，QQQ 是 19.7%，差不多；但最大回撤 −45%，比 QQQ 的 −35% 深，而且輸贏是一段一段的：2016 到 21 年每年落後 20 點，2022 年之後每年領先 22 點。這張回測的參數用過這段資料，不算樣本外；更早的 v3 參數只用 2022 年之後的資料挑，拿 2016 到 21 年當樣本外驗證，也是年化 8.6% 對 QQQ 25%。因子搜尋試了 696 條公式，也沒有一條過多重檢定門檻，所以我不宣稱有 alpha，也就是不宣稱有超額報酬。這套系統練的是驗證跟 fail-closed 的習慣，跟做晶片驗證的思路一樣。
